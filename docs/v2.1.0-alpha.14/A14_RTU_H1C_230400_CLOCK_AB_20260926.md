# Alpha14 — RTU-H1C — A/B de reloj UART a 230400

Fecha: 2026-09-26

## Objetivo

Comprobar causalmente si el fallo reproducible de 230400 esta ligado a la
fuente automatica REF_TICK del ESP32 clasico.

## Evidencia previa

H1/H1B mostraron:

```txt
230400 AUTO -> effective 231884 -> CRC masivo
250000 AUTO -> effective 250000 -> limpio
460800 AUTO -> effective 460929 -> limpio
500000 AUTO -> effective 500000 -> limpio
```

El core versionado selecciona REF_TICK para baud <= 250000 y APB por encima.

## Contrato del core

`HardwareSerial::setClockSource()` debe llamarse antes de `begin()`.

Por ello H1C usa firmware recien cargado y ejecuta primero el control AUTO.
Solo despues fuerza APB mediante:

```cpp
JWPLC_RS485.serial().setClockSource(UART_CLK_SRC_APB);
```

No se cambia la API publica del package por esta prueba.

## Casos

| Caso | Baud | Clock | Gap | TCP | Duracion |
|---|---:|---|---:|---|---:|
| CONTROL_AUTO | 230400 | AUTO / REF_TICK esperado | 500 us | OFF | 30 s |
| APB_FORCED | 230400 | APB explicito | 500 us | OFF | 30 s |

Ambos usan:

```txt
8N1
ASYNC
TX QUEUED
RTU UNPACED
FULL_RUNTIME ACTIVE
A/B/GND
```

## Criterio causal

Resultado fuerte esperado:

```txt
CONTROL_AUTO -> RTU_CLEAN=NO
APB_FORCED   -> RTU_CLEAN=YES
```

El runner registra requested/effective baud, error porcentual, RTU Hz,
failed, timeout y CRC en ambos extremos.

Si se obtiene REF_TICK_FAIL / APB_PASS, la fuente de reloj queda fuertemente
implicada como causa del problema de 230400 y se podra diseñar la politica AUTO
de clock del package sobre evidencia fisica.

Si ambos pasan o ambos fallan, H1C queda inconcluso y no se modifica la
politica final.

## Gate versionado

El gate exige un firmware recien compilado/subido para conservar intacto el
estado AUTO antes del primer caso. El orden es deliberado:

```txt
1. CONTROL_AUTO 230400
2. APB_FORCED 230400
```

No se invierte el orden porque `setClockSource(UART_CLK_SRC_APB)` persiste en
la instancia UART y la API publica de HardwareSerial no expone una operacion
equivalente a volver al estado interno "sin fuente explicita".

El gate:

1. valida branch, core candidato, archive RTU e indice;
2. verifica estaticamente el contrato del core de clock UART;
3. oculta temporalmente el archive RTU y fuerza build/upload desde source;
4. confirma objetos `JWPLC_ModbusRTU.cpp.o` y `JWPLC_RS485.cpp.o`;
5. restaura el archive anterior con el mismo SHA-256;
6. ejecuta 30 s AUTO y 30 s APB_FORCED con TCP OFF;
7. solo cierra como causal si AUTO falla y APB queda limpio;
8. pide observacion fisica de ambas TFT;
9. verifica hashes y estado Git al final.

Resultado esperado fuerte:

```txt
RTUH1C_CAUSAL_RESULT=AUTO_FAIL_APB_PASS
A14_RTU_H1C=PASS_CAUSAL_CLOCK_SOURCE
```

Si el patron no aparece, el runner sale con revision inconclusa y no se cambia
la politica de clock del package.



## Resultado ejecutado

H1C se ejecuto fisicamente el 2026-09-26 con Master COM14 y Slave COM4.

| Caso | Effective baud | Error | RTU Hz | Failed | Timeout | CRC Master | CRC Slave | Resultado |
|---|---:|---:|---:|---:|---:|---:|---:|---|
| AUTO / REF_TICK | 231884 | +0.6441 % | 289.275 | 3373 | 300 | 3073 | 300 | FAIL |
| APB_FORCED | 230423 | +0.0100 % | 380.511 | 0 | 0 | 0 | 0 | PASS |

Contadores del caso APB:

```txt
STARTED=11418
COMPLETED=11418
SUCCESS=11418
FAILED=0
TIMEOUTS=0
MASTER_CRC=0
SLAVE_CRC=0
```

Ambas TFT fueron observadas fisicamente estables.

Cierre:

```txt
RTUH1C_CAUSAL_RESULT=AUTO_FAIL_APB_PASS
A14_RTU_H1C=PASS_CAUSAL_CLOCK_SOURCE
```

## Decision derivada

La policy automatica del core no es adecuada para el puerto RS-485 del
JWPLC Basic v2 a 230400 baud: REF_TICK introduce un error efectivo medido
suficiente para destruir la comunicacion en este montaje.

La siguiente prueba es RTU-H1D. Su candidato fuerza APB desde
`JWPLC_RS485.begin()` solo en ESP32 clasico y revalida la matriz completa de
baud antes de adoptar la policy como comportamiento final.
