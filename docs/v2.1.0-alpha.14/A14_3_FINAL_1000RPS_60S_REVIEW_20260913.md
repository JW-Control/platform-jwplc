# Alpha14.3 — Regresión final FULL_RUNTIME_REALISTIC @ 1000 req/s × 60 s — REVIEW

Fecha: 2026-09-13

## Resultado

La regresión final de `FULL_RUNTIME_REALISTIC` a `1000 req/s` durante `60 s`, ejecutada después de:

- validar el refresh L2 productivo;
- cerrar el problema de aged reaccept;
- aplicar la política microSD de archivo persistente con `flush` cada 5 registros;

no alcanzó el criterio de cierre.

Clasificación:

Por tanto, la caída de throughput se clasifica inicialmente como saturación limpia / degradación de latencia, no como fallo del protocolo Modbus TCP.

## Hallazgo microSD

La política de append persistente sí quedó activa:

```text
SD_APPEND_FILE_OPEN=YES
SD_FLUSH_EVERY_RECORDS=5
SD_APPEND_CYCLES=60
SD_APPEND_FAILS=0
SD_FLUSH_CYCLES=12
```

Sin embargo, la verificación concurrente del mismo archivo falló en `11/12` ciclos:

```text
SD_VERIFY_CYCLES=12
SD_VERIFY_FAILS=11
SD_VERIFY_MAX_US=10950
PERIPHERAL_FAILURE_COUNT=11
SD_POLICY_RUNTIME=FAIL
```

El harness mantiene un `JWPLCFile` abierto en `FILE_APPEND` y, cada 5 s, abre un segundo handle `FILE_READ` sobre el mismo archivo para verificar el último registro. Esta combinación queda bajo sospecha.

`JWPLCFile` protege cada operación individual con el mutex SPI compartido, pero esa protección no implica coherencia entre dos handles simultáneos sobre el mismo archivo FAT. El modo `FILE_APPEND` del stack ESP32 equivale a `"a"` y el read separado a `"r"`.

Hipótesis principal a comprobar:

```text
SD_VERIFY_ROOT_CAUSE=SUSPECT_SIMULTANEOUS_APPEND_AND_READ_HANDLES
```

No se considera todavía demostrado; debe aislarse con un gate específico.

## Interpretación del rendimiento

No se debe atribuir todavía la reducción `95.478 % -> 90.089 %` exclusivamente a la nueva política SD.

Motivos:

- la corrida actual tiene fallos funcionales de verificación SD;
- el runner es síncrono y a ~1 kHz es muy sensible al promedio de latencia por request;
- `LATENCY_AVG_US=1100.3` es suficiente por sí solo para limitar la tasa lograble a alrededor de 900 req/s;
- los picos periódicos siguen siendo del orden de 16–21 ms;
- hace falta aislar primero la política SD correcta y luego repetir la misma corrida para separar regresión real de variabilidad de ejecución.

## Decisión

No ejecutar todavía el soak de 30 minutos.

Secuencia obligatoria:

1. aislar y corregir la verificación SD manteniendo la política de append persistente;
2. volver a ejecutar `FULL_RUNTIME_REALISTIC @ 1000 req/s × 60 s`;
3. si el resultado queda limpio y `>=95 %`, ejecutar el soak final de 30 minutos;
4. si sigue por debajo de 95 %, realizar A/B controlado para cuantificar si la caída proviene de SD, del runner/host o de otra carga del full runtime.
