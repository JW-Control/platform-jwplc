# Alpha14 — H3E — Cierre técnico de hardening RTU / Display / precompiled

Fecha: `2026-09-28`

Rama:

```text
v2.1.0-alpha.14/feature/modbus-tcp
```

## Clasificación

```text

H3E_HARDWARE_FAILURE=NO
H3E_FINAL_FULL_RUNTIME=PASS
H3E_PRECOMPILED_ARTIFACTS=QUALIFIED_AND_ADOPTED
```

Este documento cierra la etapa H3E iniciada después del cierre histórico de
Alpha14 del 13-sep. No reemplaza la evidencia A14.1-A14.5; la complementa con
el hardening posterior de runtime, Display, core y Modbus RTU.

## 1. Problema investigado

Durante full runtime se observaron gaps de servicio RTU del orden de ~20 ms.

H3E se abrió para atribuir esos gaps antes de optimizar periféricos a ciegas.

La cadena causal quedó demostrada como:

```text
loopTask
  -> taskYIELD
     -> jwplcSystemTask
        -> jwplcSystemDisplayHook
           -> renderer Display
```

No se confirmó como causa dominante:

```text
SD
FRAM
RTC
TCA/I-O
buttons
Ethernet
mutex SPI
SPI prepare
```

## 2. H3E.0 / H3E.0B — atribución al SystemTask

H3E.0 mostró que el peor gap original estaba casi completamente fuera de los
bloques visibles del sketch.

Ejemplo representativo:

```text
RTU_SERVICE_GAP_MAX_US=20659
LOOP_GAP_MAX_US=20657
H3E_WORST_UNACCOUNTED_US=20578
H3E_WORST_UNACCOUNTED_PCT=99.608
```

H3E.0B instrumentó el runtime y atribuyó el coste al Display dentro de
`jwplcSystemTask`.

En el peor evento del baseline con archive histórico:

```text
OUTSIDE_TOTAL ~= 24.538 ms
TASK_YIELD    ~= 23.699 ms
SYS_ACTIVE    ~= 23.674 ms
SYS_DISPLAY   ~= 23.629 ms
```

El tiempo activo del SystemTask estaba prácticamente dominado por Display.

## 3. H3E.1 — atribución interna de Display

El profiler profundo separó:

```text

page clear
user callback

```

Conclusión:

```text

SPI PREPARE=NO DOMINANTE
DRAW_DIRTY=DOMINANTE

```

Por tanto no se justificaba retirar periféricos ni aumentar timeouts como
solución al cuello observado.

## 11. Incidencias de harness del cierre H3E.5

### F065 — selección de librería inferida sólo desde formato verbose

H3E.5 interpretó inicialmente:

```text
DISPLAY_SELECTED=False
JWPLC_TFT_SELECTED=False
MODBUS_RTU_SELECTED=False
```

aunque simultáneamente había demostrado:

```text
*_PRECOMPILED=True
*_SOURCE_OBJECT_COUNT=0
```

Causa:

- el parser buscaba sólo `Using library ... at version`;
- el compile normal sin `-v` reporta selección mediante la tabla
  `Used library / Version / Path`.

Clasificación:

```text
HARNESS_FAILURE=YES
PRODUCT_FAILURE=NO
HARDWARE_FAILURE=NO
PHYSICAL_RESULT_INVALIDATED=NO
```

Corrección:

- aceptar ambos formatos;
- mantener prueba independiente de precompiled;
- mantener prueba por ausencia de source objects.

### F066 — transformación remota de regex corrompió temporalmente el script

Durante la corrección F065, una sustitución programática interpretó una
secuencia especial del lenguaje anfitrión dentro de una regex PowerShell y
expandió accidentalmente el archivo.

La corrupción fue detectada antes de que el usuario hiciera pull.

Clasificación:

```text
PREVENTIVE_NEAR_MISS=YES
USER_EXECUTION_FAILURE=NO
PRODUCT_FAILURE=NO
HARDWARE_FAILURE=NO
```

Corrección:

- restaurar desde HEAD sano conocido;
- reaplicar únicamente el bloque requerido;
- releer región completa;
- comparar diff net contra baseline.

Regla reforzada:

```text
PATCH
-> RE-READ
-> DIFF SIZE/SHAPE
-> REAL SYNTAX PREFLIGHT
-> CONTRACT CHECK
-> HANDOFF
```

### F067 — revalidador offline asumió UTF-8 para log de Windows PowerShell 5.1

El primer H3E.5R encontró artifacts y build directories pero no reconoció
ninguna línea del compile log.

Causa:

- P5-B escribe native output mediante `*> $LogPath`;
- Windows PowerShell 5.1 puede serializar ese texto como UTF-16;
- el lector Python forzaba UTF-8.

Clasificación:

```text
HARNESS_FAILURE=YES
PRODUCT_FAILURE=NO
HARDWARE_FAILURE=NO
PHYSICAL_RESULT_INVALIDATED=NO
```

Corrección:

- BOM detection;
- fallback UTF-16 LE/BE por NUL distribution;
- UTF-8 normal;
- CP1252 fallback;
- `python -m py_compile` previo a la revalidación.

Recuperación:

```text
PYTHON_SYNTAX=PASS
A14_H3E5_EXISTING_RUN_REVALIDATION=PASS
```

## 13. Lo que H3E no cierra

H3E no equivale por sí solo al cierre/publicación completa de Alpha14.

Siguen sujetos al checklist global del alpha, según corresponda:

- auditoría final Arduino CLI / Arduino IDE;
- documentación consolidada;
- benchmark/build policy pendiente que aplique al cierre;
- PR técnico;
- CI;
- publicación/pre-release;
- instalación aislada del package publicado;
- compile/upload físico post-publicación;
- cierre documental global.

No asumir OpenPLC integrado, OTA definido, FlashFreq final ni bootloader final.
