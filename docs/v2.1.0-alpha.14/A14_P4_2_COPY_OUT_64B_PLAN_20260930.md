## Helper real

La ruta activa es:

```text
W5100Class::read()
 -> SPI.jwplcReadBytesReuseFifo()
 -> jwplcSpiReadBytesReuseFifoNL()
```

Para cada chunk, el helper actual:

1. limita `c_len` a 64 B;
2. conserva el cache DLEN local de P4.1;
3. ejecuta la transferencia sin rellenar FIFO MOSI;
4. copia `c_longs` words mediante un loop dinámico;
5. usa una ruta especial para el último word parcial.

La copia actual de un chunk completo equivale a:

```cpp
for (uint32_t i = 0; i < 16U; ++i) {
  result[i] = dev->data_buf[i];
}
```

## Única variable causal

```text
ONLY_VARIABLE=FULL_64B_COPY_OUT_POLICY

BASELINE:
  dynamic word loop for every complete chunk

CANDIDATE:
  exactly 16 explicit volatile word loads/stores when c_len == 64
```

Nombre del switch compile-time:

```text
JWPLC_SPI_FIFO_REUSE_COPY_OUT_64=0
```

El candidato queda OFF por defecto hasta completar el A/B físico. El source se
estructura para que el bloque explícito sea sintácticamente compilable sin
alterar la API pública.

## Diseño

Para `c_len == 64` y sólo cuando el switch esté activo:

```text
result[0]  = dev->data_buf[0]
...
result[15] = dev->data_buf[15]
```

Restricciones:

- no usar `memcpy` sobre registros `volatile`;
- no cambiar DLEN, arranque ni espera `cmd.usr`;
- no cambiar frecuencia, modo SPI, CS ni ownership;
- no cambiar el avance de `out`/`len`;
- no cambiar la ruta tail de 1–63 B;
- no cambiar `W5100Class::read()` ni `EthernetClient::read()`;
- no añadir estado persistente;
- no cambiar APIs Arduino legacy.

El objetivo es retirar el branch/incremento/comparación de las 16 iteraciones
del caso dominante de 64 B, manteniendo exactamente las mismas 16 lecturas
MMIO y 16 escrituras de salida.

## Source contract

El gate estático debe demostrar:

```text
FIFO_REUSE_DEFAULT=1
DLEN_REUSE_DEFAULT=1
COPY_OUT_64_DEFAULT=0
DIRECT_RX_DEFAULT=0
W5500_SPI_HZ=26000000
RX_COMMIT_POLICY=IMMEDIATE
PUBLIC_API_CHANGED=NO
```

También debe comprobar que el fast path aparece únicamente dentro de
`jwplcSpiReadBytesReuseFifoNL()` y está condicionado por
`c_len == 64U`.

## Validación de build

Antes de tocar hardware:

1. RE-READ del helper completo;
2. parse/syntax de los scripts y source contract;
3. `jwplc_build` limpio del firmware Master;
4. `jwplc_build` limpio del firmware Slave;
5. confirmar SPI y Ethernet desde source;
6. confirmar Modbus RTU source-first;
7. confirmar ausencia de archives stale.

No se usa Arduino CLI manual para estos builds.

## Gate físico posterior

La corrección de performance requiere A/B físico porque un build sólo demuestra
composición, no integridad de payload ni reducción temporal.

Orden obligatorio:

1. FNV del candidato;
2. microperfil BASELINE vs COPY_OUT_64;
3. A/B alternado sin profiler;
4. revisión física;
5. clasificación;
6. promoción sólo si los datos lo justifican.
